# 开发运维宪法（最高约束）

冲突裁决：宪法 > README > 聊天记录 > LLM 建议。
适用：零经验新手 + LLM 协作。目标：不修坏、可回退、留痕。

## 总则（不可违背）
- C1 系统不比改前更坏。修不好可留痕，修坏不可接受。
- C2 只修现场 bug，潜在隐患只标记不修。
- C3 改动必可回退、可溯源、可解释。

## 角色边界
- R1 新手=决策者/责任人；LLM=写码字典。LLM 重构建议仅参考，最终由新手拍板，只采纳最小必要改动。
- R2 LLM 不知真机状态。所有"应可跑"在真机/中控屏验证前均为假设。
- R3 无兜底：改前自问"改坏能否自恢复到上一版"，答不出就别改。
- R4 禁止把判断权交 LLM。改动须能手册链路图讲清"改了哪环、影响哪些下游"，讲不清不做。

## 读系统
- RD1 按手册第2节顺序读，先全局后局部。
- RD2 读时画依赖：每模块记"接收/发出"。
- RD3 专名→手册词汇表→速查表→最后问 LLM。
- RD4 问题即标记，不积压。
- RD5 读懂阶段零修改，禁为读懂而改码。

## 改系统（解耦优先）
- MG1 现场bug才修，潜在bug只标（区别见下）。
  - 现场bug=真机正在发生、可复现、影响使用（白屏/某灯不动）→ 可修。
  - 潜在bug=静态扫出、未复现、不影响当前 → 只标不修。
- MG2 最小改动单元：一次一文件一函数一问题。禁顺手整理附近码。
- MG3 解耦三问（全 yes 才做）：①影响其他楼层/设备同名逻辑？②改 MQTT topic/TCP 帧/点号/JS Bridge 方法名 硬协议？③能单独回退不动其他文件？任一会→禁。
- MG4 硬协议边界绝对禁动（动一处全线崩）：
  - MQTT 主题：`/jyc/control` `/jyc/getData` `/jyc/close` `/jyc/heartbeat` `/jyc/heartbeatback` `/jyc/reboot` `/yzyl/control`
  - TCP 部署帧：4字节长度前缀 + type 1/2/3/4
  - 设备点号分段（见速查表第1节）
  - JS Bridge 签名：`relay` / `sync` / `sendMqtt` / `updateHopeLightBarColor`
- MG5 PC 工具`中控上传程序.exe`禁改（Win二进制，本环境不可编译/验证），仅当协议参考。
- MG6 Node-RED 流改动须记：改了哪个节点、影响哪类设备、前端/App 是否配套；流与 App 版本锁定。
- MG7 外部依赖禁动：`netty`/`paho`/`hutool`/`ini4j`/`fastjson`、`build.gradle` 无明确理由不改。
- MG8 不可验证改动禁做（转标记）。
- MG9 改后必过冒烟 checklist（第7章）。

## 模块化
- M1 禁整体重构/换框架/引入新架构。
- M2 仅新增功能或修bug被迫时局部收拢成小函数/类。
- M3 新逻辑新建文件/函数，老函数保持原样，新码经调用接入。
- M4 新模块在手册第3节补"接收/发出"，速查表补点号。
- M5 拒 LLM"顺手重构"，回"只做最小必要改动"。

## 文档即代码（双向铁律）
- D1 改一处码=至少同步更新对应文档；文档过时=系统损坏，视为改动未完成、禁上线。
- D2 代码即文档：源码白话注解集中 `docs/代码解说/`（源码镜像，码改解说必改）。
- D3 硬同步清单（改后逐项核对）：
  1. 改 Java/JS/节点行为 → 更新 `代码解说/` 对应文件
  2. 改模块接收/发出或新增模块 → 更新 `系统解剖手册.md` 第3节
  3. 改点号/协议/设备映射 → 更新 `设备点号速查表.md`
  4. 改码 → `演化日志.md` 写 E-xx（日期/触发/文件/动机/改法要点/回退/验证）
  5. 修bug → `工作日志.md` B 清单标 `<已修复-日期>` + 修复记录
- D4 令 LLM 改码须同时要求产出文档更新 diff；只给码不给文档更新→新手自补或拒该改动。
- D5 演化日志为变更史真相源，倒序、唯一编号 E-xx，字段固定（见 D3.4）。
- D6 违反后果：基于错误地图极可能修坏，比不改更危险。宁可慢不可不同步。

## 运维与 bug 脚手架
- OP1 日志第一优先级。关键分支加 `Log.d/x`（Android 前缀 `JYC-`，便于 `logcat|grep JYC-`）或 Node-RED `debug`。
- OP2 状态可观测：`save.json`/`conf.ini`/logcat 三大排障源，改后确认仍可读可定位。
- OP3 留痕三件套：工作日志记录 + B清单修复记录 + 手册/速查表同步。
- OP4 版本配套表：App/Node-RED流/前端/PC工具 任升记一行，防协议漂移。
- OP5 回退预案：改前备份（git commit 或 `.bak`）；conf.ini/save.json 改前复制原文件，写明回退步骤。
- OP6 未知bug SOP：复现→logcat(`JYC-`)→save.json→Node-RED debug→定位链路→速查表点号→小额改动验证。
- OP7 不掩盖错误：catch 禁打空/吞异常，至少 `Log.e` 留痕。

## 冒烟 checklist（每次必过）
- [ ] 真机/中控屏启动不白屏（核对 conf.ini `web` 指向真实入口）
- [ ] 改动涉及楼层/设备类型功能正常（不只测改点）
- [ ] 未改楼层/设备类型行为无变化（解耦验证）
- [ ] MQTT 能连（aedes 39201）、心跳正常
- [ ] 改前端：原样部署可加载；改 App：APK 可静默装
- [ ] logcat 无新增 crash；Node-RED debug 无异常
- [ ] 三件套文档已更新
- [ ] 回退预案已备

## 禁止项（红线）
- X1 整体重构/换框架/新架构
- X2 动硬协议边界（MG4）
- X3 改 PC 工具二进制
- X4 修非现场未复现潜在 bug
- X5 不可回退改动
- X6 不可验证改动
- X7 改编译配置/依赖版本（无理由）
- X8 "顺手优化"/LLM 重构建议
- X9 吞异常/空 catch
- X10 改码不同步文档
- X11 无备份改 conf.ini/save.json
- X12 凭 LLM 一句话上线未经真机验证

## 演进
- E1 宪法未覆盖且踩坑→先按"不修坏+可回退+留痕"处理，再补对应章。
- E2 改宪法须在 `工作日志.md` 记一条（为何改、改了哪条）。
- E3 项目完工且经验积累后可放宽部分限制，须显式记录理由与范围。
