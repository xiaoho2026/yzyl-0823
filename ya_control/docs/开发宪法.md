# 亚中中控系统 · 开发运维宪法（Project Constitution）

> **性质**：本项目最高约束文档（"宪法"）。任何读系统、改系统、运维动作的优先级都低于本文件。
> 当 LLM 建议、README、聊天记录与本文件冲突时，**以本文件为准**。
> **适用对象**：零经验、无指导者、借助 LLM 的新手工程师；当前与未来所有接手者。
> **目标**：在"未完成、无经验、怕修坏"的现实下，安全地把项目做完、长期运维、并为未来未知 bug 留足排查条件。
> **上下文治理（重要）**：本文档**长驻上下文**（每次会话都应加载）。其余文档按 `docs/上下文路由.md` **按需加载**，
> 禁止一次性全读导致上下文爆炸/污染。代码解说已分片，只读本任务相关单文件。

---

## 第 1 章 · 总则（三条不可违背的底线）

1.1 **系统不能比改之前更坏。** 任何改动的第一目标不是"修好"，而是"不引入新问题"。修不好可以留痕，修坏不可接受。
1.2 **只动现场正在发生的 bug，不主动修静态隐患。** 非现场、未复现的问题，一律进 `docs/工作日志.md` 的 B 清单**标记**，不修。
1.3 **改动必须可回退、可溯源、可解释。** 改之前想清楚"怎么回去"，改之后立刻写文档。不可回退的改动禁止做。

---

## 第 2 章 · 角色边界（新手 + LLM 的分工）

2.1 **新手是决策者和责任人**，LLM 是"会写代码的字典"，不是架构师。LLM 提的"建议重构/优化"可参考，**最终是否做由新手拍板，且只采纳最小必要改动**。
2.2 **LLM 不知道真机状态**。所有"应该能跑"的判断在真机/中控屏验证前都只是假设。新手必须亲自验证，不能因为 LLM 说"没问题"就上线。
2.3 **无指导者意味着没有兜底**。改动前自问："如果这次改完屏黑了/灯不亮了，我能否自己恢复到上一版？"答不上来就别改。
2.4 **禁止把判断权完全交给 LLM**。LLM 给出的修复方案，新手须能用 `docs/系统解剖手册.md` 的链路图讲清楚"它改的是链路哪一环、影响哪些下游"，讲不清就不做。

---

## 第 3 章 · 读系统规则（理解原系统）

3.1 **按 `docs/系统解剖手册.md` 第 2 节顺序读**，不跳、不硬啃。先全局后局部。
3.2 **读时画依赖**，不只读代码。每个模块记录"它接收什么 / 发出什么"（手册第 3 节已给模板）。
3.3 **遇到不懂的专有名词先查手册第 7 节词汇表**，再查 `docs/设备点号速查表.md`，最后才是问 LLM。
3.4 **读出来的问题立刻标记**，不积压。能确定是 bug 的进 B 清单；只是疑问的记在手册/日志的"待确认"区。
3.5 **禁止为"读懂"而改代码**。读阶段零修改，纯观察。任何"顺便改一下"的冲动延后到完工/运维阶段按第 4 章走。

---

## 第 4 章 · 改系统规则（铁律 · 解耦优先）

> 本章是新手最该死记的部分。**"不牵一发而动全身"是最高原则。**

4.1 **现场 bug 才修，潜在 bug 只标。** 区别：
   - 现场 bug = 当前真机上正在发生、能复现、影响使用的（如白屏、某灯点不动）。→ 可修（按 4.2~4.9）。
   - 潜在 bug = 静态扫出、未复现、不影响当前的（如 B 清单里大部分）。→ **只标不修**。

4.2 **最小改动单元（MIT 原则）**：一次只改一个文件、一个函数、解决一个问题。禁止"顺手"把附近代码也整理。
4.3 **解耦三问**（动手前必答，全答 yes 才做）：
   - 改这块，会不会影响**其他楼层/其他设备类型**的同名逻辑？（会→不能动，或抽公共不改原调用）
   - 改这块，会不会改变**MQTT topic / TCP 帧 / 点号 / JS Bridge 方法名**这几条硬协议？（会→禁止，除非四层部署物同步改且能验证）
   - 改这块，能不能**单独回退**而不动其他文件？（不能→禁止）
4.4 **硬协议边界（地基）绝对不可动**：
   - MQTT 主题：`/jyc/control`、`/jyc/getData`、`/jyc/close`、`/jyc/heartbeat`、`/jyc/heartbeatback`、`/jyc/reboot`、`/yzyl/control`
   - TCP 部署帧格式（4 字节长度前缀 + type 1/2/3/4）
   - 设备点号分段（见速查表第 1 节）
   - JS Bridge 方法签名 `relay / sync / sendMqtt / updateHopeLightBarColor`
   > 这些动一处，App↔Node-RED↔前端↔PC工具全线崩。新手**永远不主动改**。

4.5 **PC 工具（`中控上传程序.exe`）不可改**：它是 Windows 二进制，无法在本环境编译/验证。只能当协议参考。若发现需改部署协议，记录为需求，不落地。
4.6 **Node-RED 流改动需配套记录**：改 `亚中.json` 任何节点，必须在日志写清"改了哪个节点、影响哪类设备、前端/App 是否要配套"。流与 App 版本须锁定对应。
4.7 **外部依赖不动**：`netty / paho / hutool / ini4j / fastjson` 等库版本、`build.gradle` 编译配置，无明确理由不改（改了可能整体编不过，新手难救）。
4.8 **不可验证的改动禁止做**：无法在真机/中控屏/模拟环境验证的修改（如纯逻辑且无法触发），不落地，转标记。
4.9 **改动后必做冒烟 checklist**（见第 7 章），全过才算改完。

---

## 第 5 章 · 模块化规则（局部渐进，不整体重构）

5.1 **不整体重构**。原架构（单 Activity + WebView + Node-RED 翻译）保持不变，不引入新框架、不拆分大文件做"优雅化"。
5.2 **局部模块化**：只在"新增功能"或"修 bug 被迫"时，把相关代码收拢成小函数/小类，命名清晰、职责单一。
5.3 **新增代码单独成块**：新逻辑尽量新建文件/新函数，不往老函数里塞。老函数保持原样，新代码通过调用接入（降低回退成本）。
5.4 **文档即模块边界**：每个新模块/新函数在 `docs/系统解剖手册.md` 第 3 节补一行"接收/发出"，在速查表补点号（如新增设备）。
5.5 **拒绝 LLM 的"顺手重构"**：LLM 常建议"这个文件太乱，重构成 X 模式"。新手一律拒绝，回复"只做最小必要改动"。

## 第 5B 章 · 文档即代码（最高原则之一，双向约束）

> 本章把"文档即代码"定为铁律，分两层。**任何代码改动若未同步文档，视为改动未完成、禁止上线。**

### 5B.1 代码即文档（理解阶段 · 不改源码）
- 当前系统是未完工、无注释、无经验的，新手靠**"代码解说文档"**理解，而非改源码加注释（宪法 3.5 禁止为读懂而改代码）。
- 所有源码的"白话注解"集中放 `docs/代码解说/`：逐文件、逐关键函数，用新手能懂的话写"它干嘛、接收什么、发出什么、坑在哪"。
- 代码解说文档是**源码的镜像**，不是源码的副本。源码改了，解说必须跟着改（见 5B.2）。

### 5B.2 文档即代码（开发运维阶段 · 改代码必改文档）
- **铁律**：改一处代码 = 至少同步更新对应文档。文档过时 = 系统损坏。LLM 和新手都靠文档判断"系统现在是什么样"，文档与代码不一致会直接导致误改、修坏。
- **硬性同步清单**（改动后逐项核对，缺一不可）：
  1. 若改了某 Java/JS/Node-RED 节点的行为 → 更新 `docs/代码解说/` 对应文件的解说块。
  2. 若改了模块"接收/发出"或新增模块 → 更新 `docs/系统解剖手册.md` 第 3 节。
  3. 若改了点号/协议/设备映射 → 更新 `docs/设备点号速查表.md`。
  4. 若改了代码 → 在 `docs/演化日志.md` 写一条演化记录（见 5B.3），包含：版本/commit、改了哪些文件、为什么改、怎么改的、如何回退、验证结果。
  5. 若修复 bug → 在 `docs/工作日志.md` 的 B 清单标 `<已修复-日期>` 并补修复记录。
- **LLM 协作纪律**：让 LLM 改代码时，**必须同时要求它产出对应的文档更新 diff**；若 LLM 只给代码不给文档更新，新手须自己补，或拒绝该改动。

### 5B.3 演化日志（让 LLM 与未来的自己知道"是什么、如何发生"）
- 位置：`docs/演化日志.md`，按时间倒序，每条带**唯一演化编号 E-xx**。
- 每条必含字段：**日期 / 触发（现场bug or 需求）/ 改动文件清单 / 动机 / 具体改法（要点，不给大段代码）/ 回退方式 / 验证 / 关联文档**。
- 演化日志是系统的"变更史"，未来排障时先翻它，判断"这个行为是不是某次改动引入的"。
- 初始基线：项目复制进工作区时记一条 `E-00 初始基线`，固化"读懂时的系统原貌"，作为所有后续演化的对照锚点。

### 5B.4 违反后果
- 代码改了文档没改 → 下次读取会基于错误地图，极可能修坏。这比"不改"更危险。
- 因此：**宁可慢，不可不同步文档。** 宪法第 1.1 条（不比改之前更坏）包含"文档不比改之前更旧"。

## 第 6 章 · 运维与 bug 脚手架（为未来 unknown bug 留路）

> 核心诉求：新手未来对 bug 无经验判断，现在就要给"未来的自己/接手者"留足排查条件。

6.1 **日志是第一优先级**。所有新增/修改的逻辑，关键分支加 `Log.d/x` 或 Node-RED `debug` 节点，输出"收到什么/发出什么/结果"。
   - Android：`Log.d("JYC-<模块>", "...")` 统一前缀 `JYC-`，方便 `logcat | grep JYC-` 过滤。
   - Node-RED：关键节点接 `debug` 节点（已有 `debug 35` 等范例）。
6.2 **状态可观测**：`save.json`（设备状态）、`conf.ini`（配置）、App logcat 是三大排障源。改动后确认这三者仍可读、可定位。
6.3 **改动留痕三件套**（缺一不可）：
   - 在 `docs/工作日志.md` 写一条"阅读/工作记录"（做了什么、涉及文件、结论）。
   - 若修复 bug，在 B 清单对应行标 `<已修复-日期>` 并补"修复记录"块。
   - 若改了代码导致地图文档过时，同步更新 `系统解剖手册` / `设备点号速查表`（文档过时 = 系统损坏）。
6.4 **版本配套表**：维护一份"部署物版本矩阵"（App版本 / Node-RED流版本 / 前端工程版本 / PC工具版本），任一升级都记一行，避免协议漂移。
6.5 **回退预案**：每次改动前，备份被改文件（git commit 或复制 `.bak`）；conf.ini / save.json 改动前先复制原文件。写明"回退步骤"进日志。
6.6 **未知 bug 排查 SOP**（写入手册第 6.4 节，未来照着走）：先复现→查 logcat(`JYC-`)→查 save.json→查 Node-RED debug→定位链路环节→查速查表点号→小额改动验证。
6.7 **不掩盖错误**：catch 里不打空、不吞异常；至少 `Log.e` 留痕，让未来能看到"这里曾经炸过"。

## 第 7 章 · 改动后冒烟 checklist（每次必过）

- [ ] 真机/中控屏能启动，不白屏（核对 `conf.ini` 的 `web` 指向真实入口）
- [ ] 改动涉及的楼层/设备类型功能正常（不只测改的那一个点）
- [ ] 未改的楼层/设备类型行为无变化（解耦验证）
- [ ] MQTT 能连（aedes 39201）、心跳正常
- [ ] 若改前端：原样部署后能加载；若改 App：APK 能静默安装
- [ ] logcat 无新增 crash；Node-RED debug 无异常
- [ ] 三件套文档已更新（日志 + B清单/修复记录 + 手册/速查表）
- [ ] 回退预案已备（备份在、步骤明）

---

## 第 8 章 · 禁止项（红线）

8.1 禁止整体重构 / 换框架 / 引入新架构模式。
8.2 禁止动硬协议边界（第 4.4 条所列）。
8.3 禁止改 PC 工具二进制。
8.4 禁止修非现场、未复现的潜在 bug（只标）。
8.5 禁止不可回退的改动。
8.6 禁止不可验证的改动。
8.7 禁止改编译配置/依赖版本（无明确理由）。
8.8 禁止"顺手优化"——LLM 提的重构类建议一律拒绝。
8.9 禁止吞异常 / 留空 catch。
8.10 禁止改代码不同步文档。
8.11 禁止在没备份 conf.ini / save.json 的情况下改它们。
8.12 禁止凭 LLM 一句话上线，未经真机验证。

---

## 第 9 章 · 本宪法的补充与演进

9.1 本宪法可能不完整。新手在实战中遇到"宪法没覆盖、且踩了坑"的情况，**先按"不修坏、可回退、留痕"的总则处理，再把该情形补进对应章节**。
9.2 任何对宪法的修改，须在 `docs/工作日志.md` 记一条，说明为何改、改了哪条。
9.3 当项目"完工"且新手积累经验后，可经审慎评估放宽部分限制（如允许局部重构），但须显式记录放宽理由与范围。
9.4 宪法与三份地图文档（手册/速查表/日志）是同一体系：宪法定规则，地图供执行，日志留证据。

---

> **一句话给未来的自己**：看不懂就不改，改不动就标记，改之前先备份，改之后必写文档。
> 系统活着比系统完美重要。
