# 跨设备维护指南（macOS + Windows 10）

> **目的**：在 Mac mini 与 Windows 10 笔记本上协同维护本系统，保证文件单一事实源、不互相污染。
> **核心原则**：对话记录靠 CodeBuddy 云端续接；**项目文件靠 Git，不靠对话记忆**。

## 2. 两机工作流（日常）

```
Mac 改完  →  git add -A  →  git commit -m "..."  →  git push
Win10 接手 →  git pull
（反之同理：Win10 改 → push，Mac → pull）
```

**铁律**（与宪法一致）：
- 提交前先 `git pull` 避免冲突（尤其两机都动过）。
- 改代码必同步 `docs/` 文档 + 写 `演化日志.md` 的 E-xx（见宪法 5B 章）。
- 大改动单开分支（如 `fix/b-03`），完工地合并回 `main` 再 push。

## 3. SSH 配置要点（首次连接必做）

### 3.1 Mac 侧（已处理）
- 首次 push 遇 `Host key verification failed` → 已执行：
  ```bash
  ssh-keyscan -t rsa,ed25519 github.com >> ~/.ssh/known_hosts
  ```
- 需本机已生成 GitHub SSH key 并加到 GitHub 账号（`~/.ssh/id_rsa.pub` 或 `id_ed25519.pub`）。

### 3.2 Win10 侧（待做）
1. 安装 Git for Windows。
2. 生成 SSH key（若没有）：
   ```powershell
   ssh-keygen -t ed25519 -C "cdho2012@gmail.com"
   ```
3. 把 `C:\Users\<你>\.ssh\id_ed25519.pub` 内容加到 GitHub → Settings → SSH keys。
4. 首次 clone 同样可能需接受 host key（Git Bash 会提示，输 `yes`）。
5. clone：
   ```powershell
   git clone git@github.com:xiaoho2026/yzyl-0823.git
   ```

## 4. .gitignore 规则（为什么这样配）

| 忽略项 | 原因 | 配置位置 |
|---|---|---|
| `ya_control/local.properties` | 含**本机 SDK 路径**（Mac `/Users/...` / Win `D:\Android\...`），两机不同，绝不跨设备共享 | `ya_control/.gitignore`（Android 标准） |
| `ya_control/app/build/`、`*.gradle`、`*.iml`、`.idea/` | 编译产物/缓存，巨大且本机生成 | `ya_control/.gitignore` |
| `.DS_Store`、`.AppleDouble`、`Thumbs.db` | macOS/Win 垃圾文件 | 根 `.gitignore` |
| `.codebuddy/` | CodeBuddy 本地产物，含本机路径，不跨设备 | 根 `.gitignore` |

> **关键**：`local.properties` 被忽略 → 两机各自 Android Studio 打开时**自动生成本机版本**，互不覆盖。这是跨设备不踩坑的核心。

## 5. CodeBuddy 对话同步边界（重要，避免误判）

| 内容 | 是否跨设备同步 | 说明 |
|---|---|---|
| **对话记录（聊天历史）** | ✅ 通常能（同账号云端） | 换设备登录可见历史对话 |
| **项目文件（代码/文档）** | ❌ **不自动同步** | 必须靠 Git push/pull |
| **项目记忆/.codebuddy/** | ⚠️ 本地产物 | 已 gitignore，两机各自生成 |

**结论**：
- 对话用于**当下协作**，不代表文件状态。
- **改动以 Git commit 为准**，不以"我记得对话里说过"。
- 换设备后 LLM 上下文是新的，它不记得你上周在另一台机说了什么——靠 `演化日志.md` 的 E-xx 还原"改了什么、为什么"。
- 因此：**对话续接 ≠ 文件同步**。两者配合，不替代。

## 6. 灾难恢复

- **误改想回退**：`git log` 找提交 → `git revert <commit>` 或 `git checkout <commit> -- <文件>`。
- **本地仓库坏**：删 `yzyl-0823/` → 重新 `git clone`。
- **远程丢**：GitHub 仓库可恢复/转移，本地任一机有完整历史。
- **配置丢失**：`.gitignore` 已在仓库，clone 即得；`local.properties` 由 Android Studio 重建。

## 6B. NAS 同步协同注意事项（若叠加 NAS 备份）

> 结论：**Git 管协作（单一事实源），NAS 只做单向备份（保险丝），绝不双向实时同步工作区。**
> 详情见 `docs/元认知-记忆规范.md` 第2章反模式；此处给可操作规则。

### 6B.1 推荐方案：NAS 单向备份（最稳）
- NAS 定时（如每晚）把 Mac 上的 `yzyl-0823/` **只读归档**到 NAS 备份区。
- **不反向同步、不双向、不实时**。Git 永远是工作真相源，NAS 仅硬件容灾。

### 6B.2 禁止方案：NAS 双向实时同步 `yzyl-0823/`
会导致三类冲突（详见元认知规范）：
1. **文件锁/半写**：同步过程覆盖 `.git/objects`、`.git/index` → Git 仓库损坏。
2. **两机同时改 → 三方冲突**：NAS 自动合并与 Git 显式 commit 两套逻辑互毁。
3. **`.git` 目录互污染**：两机 `.git` 历史/refs 混杂，remote 指向错乱。

### 6B.3 若坚持用 NAS 同步（不推荐，缓解措施）
1. **排除 `.git/`、`.codebuddy/`、build、`local.properties`**（与 `.gitignore` 对齐，防本机路径污染）。
2. **禁用实时**，改手动/定时，且确保同一时刻只有一台机器在改。
3. 改完先 `git push`，再让 NAS 同步；NAS 只作第三方副本，不作工作目录。

### 6B.4 NAS 规则与 .gitignore 对齐清单
- 必须排除：`.git/`、`.codebuddy/`、所有 `build/`、`local.properties`、`*.iml`、`.idea/`、`.DS_Store`。
- 否则 Mac 的 `.codebuddy` 覆盖到 Win10 → 含本机路径 → 污染。

## 8. 双分支整合 SOP（两终端从同节点分叉且改动非独立）

> **场景**：Mac 与 Win10 从同一节点各自发展 `branchA`/`branchB`，且改动**不是独立的**（交集命中同批文件/同逻辑/同硬协议）。
> 此时不能简单"各取所长"，硬合并会互相覆盖或产生冲突。本 SOP 给出整合红线与步骤。

### 8.1 合并前必做：冲突预检（不急着 merge）
```bash
git diff --stat main..branchA
git diff --stat main..branchB
# 交集 = 两边都改的文件（冲突高发区）
comm -12 <(git diff --name-only main..branchA | sort) <(git diff --name-only main..branchB | sort)
```
- 若交集命中**宪法 4.4 硬协议边界**（MQTT topic / TCP 帧 / 点号分段 / JS Bridge 方法名）→ 两分支**本质不兼容**，禁止自动合并，必须人工裁决（见 8.3 法 A）。

### 8.2 按重叠程度选策略
| 情形 | 判断 | 做法 |
|---|---|---|
| 交集为空（实际独立） | 预检无交集 | `git merge branchA && git merge branchB`（无冲突） |
| 交集有，语义可共存 | 不同函数/楼层/设备类型 | Git 自动合并 → 跑冒烟 checklist + 解耦验证 |
| 交集有，真冲突 | 同函数/同协议字段两分支都改 | 见 8.3 三法 |

### 8.3 真冲突的三法整合法
- **法 A · 手动三路合并（推荐最安全）**：`git checkout main` → `merge branchA` → `merge branchB`（冲突爆发）。逐块对照 A 意图 / B 意图 / main 原貌。裁决：硬协议以真机验证过的那支为准；另一支回退到不改协议只调业务；保留"最小必要"那侧，吸收差异点而非整段替换。拿不准 → **不合并**，转 B 清单标记，回统一基线重做。
- **法 B · 选一主干 + rebase + cherry-pick**：`git rebase main` 把补充支重放到 main，再 `cherry-pick` 主干上有价值提交。会重写历史，须在演化日志写明"重放哪些提交、为何"（宪法 1.3 可溯源）。
- **法 C · 汇合分支（保可回退）**：`git checkout -b integrate main` → 在专门分支上 `merge branchA` + `merge branchB` 解决冲突 → 充分验证 → `checkout main` → `merge integrate`（快进）。原 branchA/B 保留作对照，整合炸了可丢弃重来。

### 8.4 本项目专属雷区
1. **硬协议漂移**：两分支若各自改 MQTT topic / 点号，合并后四层部署物（App/Node-RED流/前端/PC工具）版本不再配套 → 核对演化日志版本矩阵确保对齐（宪法 6.4）。
2. **`亚中.json` 合并极危险**：大 JSON 文本合并常产生"合法 JSON 但语义错乱"（节点重复/连线断裂）。合并后**必须用 Node-RED 编辑器打开校验**，不只信 `git merge` 成功。
3. **文档双重错位**：两分支可能都改 `docs/代码解说/` 同一文件，合并后文档与代码可能双重错位 → 按宪法 5B.2 逐项核对同步清单。

### 8.5 整合后必做
- 跑宪法第 7 章冒烟 checklist（重点验证交集文件涉及的楼层/设备无回退）。
- 核对版本矩阵（8.4.1）。
- 在 `演化日志.md` 补一条 E-xx：合并了哪些分支、交集文件、采用策略、验证结果。

### 8.6 整合红线（一句话）
> 合并前查交集；交集命中硬协议边界 → 禁自动合并，人工裁决；优先用汇合分支法 C 保可回退；`亚中.json` 合并后必用 Node-RED 校验；拿不准就不合并，转标记回基线重做。
